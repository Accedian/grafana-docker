# Path Analytics observability QA

This exercises the existing pca-pa-ingestion-pipeline dashboard with synthetic RA observations. It does not feed Kafka, RCA, PCA, or Druid. Real processing tests live in sky-topo/tests/ra-observability.sh.

For a narrated walkthrough with Grafana screenshots, companion Prometheus samples and copyable scenario commands, use the [observability demo](../../manualtestplans/pa07-observability-demo.md). The [local Grafana test plan](../../manualtestplans/pa07-observability-test-plan.md) defines the full cases.

## Run

Prerequisites: Docker with Compose, Python 3.9+ with venv, and access to the pinned public images/wheels. From the grafana-docker root:

```bash
make test-observability
make pa07-qa-up
make pa07-qa-test
```

The unit target creates and removes its own temporary venv, verifies pinned wheel hashes, runs the Python suite, and uses the pinned Prometheus image as an offline PromQL parser. The same target runs before the existing CI build/release chain; missing Docker/parser/dependencies fail rather than silently skipping checks.

The live target repeats that suite and executes [check_live.py](check_live.py) against real Prometheus and Grafana. It selects finite RA scenarios, checks every panel query and tenant discovery, and stops/restarts only this QA project's simulator to verify actual scrape failure/recovery. It finishes with a healthy restarted simulator. Do not run the drill against another project or a shared deployment.

| Service | Loopback URL |
| --- | --- |
| Dashboard | [Path Analytics QA](http://127.0.0.1:13000/d/pca-pa-ingestion-pipeline) |
| Scenario controls | [Metrics simulator](http://127.0.0.1:19999/) |
| Prometheus | [Local Prometheus](http://127.0.0.1:19090/) |

The QA Grafana engine is upstream 12.1.0, with the actual repository dashboard/datasource provisioned read-only. It has anonymous Viewer access and no basic login; every published port binds to 127.0.0.1. It contains synthetic data only and does not replace qualification of the packaged PCA image, ingress, roles, or datasource authorization.

## Scenarios and target selection

The existing ten PA collector/transport scenarios remain available. Twelve pa07-prefixed scenarios additionally model healthy activity, idle, numeric quality, source discard, row loss, failed/partial publication, stall, initialization, missing families, explicit reset, and recovery. Discover them through GET /api/scenarios or the simulator UI.

Faults default to synthetic tenant A and ra_summary. Tenant B and the other type remain healthy. POST /api/scenario accepts the existing dashboard/scenario fields plus an optional target object:

```json
{
  "dashboard": "Customer (swarm)/pca-pa-ingestion-pipeline.json",
  "scenario": "pa07-stalled",
  "target": {
    "tenant_id": "11111111-1111-4111-8111-111111111111",
    "record_type": "ra_summary"
  }
}
```

Targets are restricted to the two predefined UUIDs and ra_summary/ra_instance; arbitrary labels and per-payload identities are rejected. GET /api/state exposes ra_scenario and ra_target for verification.

Ordinary scenario/rate changes preserve counter history, including changes between scrapes. Only pa07-restart resets RA counters and never-seen timestamps. Use scenarios/targets for RA controls; generic scalar overrides of RA families are rejected. Existing non-RA counter overrides are nonnegative rates, not literal totals. Invalid/non-finite/oversized controls return HTTP 400 while preserving prior selection/overrides.

New RA metrics always have explicit profiles. Prometheus supplies real up; the simulator never invents it. The QA job is sky-topo, matching Swarm. The metrics-missing scenario omits the selected source while its scrape remains healthy. Schema-presence panels are explicitly deployment-level; absent source data must be investigated using configuration/state rather than filled with a universal zero.

Quantities and activity times answer different questions. A source message can contain many rows; input minus output is not packet loss. Quality diagnostics can accompany published rows. Output acknowledgement is not proof of Druid ingestion or exactly-once delivery. New retry/replay and delivery-policy mechanisms remain outside MVP.

## Cleanup

```bash
make pa07-qa-down
```

This stops only the named pa07-observability project, without resetting Kafka offsets or removing another project's resources. The older general simulator also now binds host ports to loopback and installs the same hash-locked dependencies.

## Dependencies and evidence limits

Image manifests are pinned in [docker-compose.qa.yml](docker-compose.qa.yml). Wheel identities are pinned in [requirements.txt](requirements.txt), from project-maintained [Prometheus client](https://pypi.org/project/prometheus-client/0.26.0/) and [PyYAML](https://pypi.org/project/PyYAML/6.0.3/) release records. Installation uses wheels only, verified before use. Profiles render through the [maintained Python exposition writer](https://prometheus.github.io/client_python/collector/custom/) and are parsed by actual Prometheus tooling.

Local QA proves labels, query behavior, control boundaries, and presentation. The Sky-Topo real-Kafka suite proves actual branch/output/offset observations. Neither provides remote PCA authorization, database-fault, capacity, or Druid-ingestion qualification by itself.
